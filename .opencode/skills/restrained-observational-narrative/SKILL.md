# AScombat 小说创作与叙事控制 Skill

## 1. 使命与适用范围

本 Skill 面向 AScombat 的长篇小说创作，提供从章节构思、正文撰写到修订和一致性检查的完整工作流。

目标不是让所有文字采用同一种腔调，而是实现以下效果：

1. 读者通过人物的生活、行动和冲突逐渐认识世界。
2. 人物只能依据当时掌握的信息行动，不得提前知道作者掌握的真相。
3. 历史信息逐步揭示，但底层事实、因果关系和叙事逻辑保持可靠。
4. 情感主要通过行为、选择、停顿、物件和关系变化呈现。
5. 每章推动事件、人物关系或读者认知至少一项发生实质变化。
6. 创作完成后，既有设定、时间线、人物状态和章节索引保持一致。

本 Skill 适用于：
- 新章节创作与续写；
- 既有章节的文学性修订；
- 场景设计与对话润色；
- 历史线索和证据揭示顺序审查；
- 人物认知、动机与关系连续性检查；
- 章节之间的事实一致性审查。

## 2. 项目规范优先级

创作前，根据任务读取必要的项目文件。

### 2.1 规范来源

- `AGENTS.md`：项目操作约定、目录规则和修改纪律。
- `docs/world.md`：世界规则、主题、三层信息结构及核心原则。
- `docs/characters.md`：人物身份、动机、秘密、缺点和人物弧线。
- `docs/timeline.md`：事件时间线。
- `docs/history.md`：历史事件及其因果。
- `docs/truth-tree.md`：历史真相的证据链。
- `docs/magic.md`：魔法运行规则与限制。
- `docs/vapor.md`：汽相技术原理、阶段和叙事揭示节奏。
- `docs/chapters.md`：四卷三十一章的总体结构。
- `docs/factions.md`、`docs/names.md`：阵营与名称规范。
- `data/*.json`：供程序读取的结构化数据。
- `drafts/`：已经写成的章节正文及前后文。

按任务需要读取文件，不必每次无差别读取整个仓库。

### 2.2 冲突处理

当不同文件出现冲突时：

1. 优先遵守 `AGENTS.md` 中的操作约定。
2. 以 `docs/` 中当前有效的规范为世界观和剧情依据。
3. 使用 `drafts/` 判断已经写出的叙事内容，但不把草稿中的偶然错误视为正式设定。
4. 将 `data/*.json` 作为结构化数据使用；发现其与规范冲突时，记录问题，不自行认定 JSON 一定正确。
5. `settings.txt` 为只读原始设定，未经明确授权不得修改。
6. `世界设定扩展.md` 是素材库，不得自动将其中每个想法写入正式设定。

发现规范之间存在实质冲突时，先报告冲突及其影响。不要通过创作正文悄悄决定哪个版本正确。

## 3. AScombat 的不可违背原则

### 3.1 核心主题

核心主题：人如何在一个被历史和政治塑造的世界里，重新认识“敌人”。

两个副主题：
- 真相并不天然带来和平。
- 技术不能决定未来，使用技术的人才决定未来。

汽相是核心隐喻：某些力量不是任何单一阵营独有的，而是在不同的人共同工作、彼此约束时产生。

任何重大情节都应当服务于人物、主题或因果链，而不是仅仅展示设定。

### 3.2 世界与历史纪律

- 不允许任何现实国家与火盟或水盟形成一对一映射。
- 不得把故事改写成一个幕后超级组织预先设计所有事件的阴谋故事。
- 矿难应由事故、延误救援、错误判断、利益计算、责任逃避和事后利用等因素共同构成。
- 不得为了反转而任意更改已经确定的历史事实。
- 魔法只能操纵既有条件，不得凭空创造物质或无限能源。
- 火盟、水盟、风光系及其他势力必须保持各自的利益、局限和内部差异。
- 不要以新增势力、新魔法、新历史原型或更复杂的阴谋代替人物与场景的发展。

### 3.3 三层信息纪律

读者对矿难的认知按三层推进：

- 第一层：矿难不像课本所写的那么简单。
- 第二层：当年有人故意延迟救援。
- 第三层：多方出于各自看似合理的行为，共同把事故推向战争。

写作前确定当前章节及场景允许触及的认知层级。

可以埋下早期读者暂时无法解释的细节，但不能通过人物的直接判断、作者解释或过于完整的证据组合提前泄露后续结论。

**读者认知可以不完整，作者内部的因果链不能不完整。**

## 4. 叙事方法

### 4.1 有限视角

每个场景必须明确叙述者或焦点人物。

只允许呈现该人物能够观察、记忆、推断或听说的内容。不得直接进入其他人物的内心，也不得让人物无缘无故掌握尚未获得的信息。

区分以下四种信息：

- 亲眼所见：人物直接观察到的事实。
- 他人所述：人物收到的信息，可能有误。
- 当时推断：人物依据现有信息形成的判断。
- 事后理解：人物后来才获得的认识。

不要将推断写成已经证实的事实。

### 4.2 观察与解释分离

优先呈现具体观察，再决定是否需要解释。

可使用的观察包括：
- 人物把什么东西放在哪里；
- 某个动作重复了几次；
- 一个人回答前停顿了多久；
- 机器、餐具、衣服或建筑发出什么声音；
- 对话中的某个人避开了什么问题；
- 人物的日常习惯发生了什么变化。

观察必须自然，不需要每个细节都有象征意义。

不要为了制造文学感，强迫人物精确测量不值得注意的事物。观察的精度应符合人物的性格、职业、注意力和当前处境。

### 4.3 克制表达与情感留白

优先让情绪通过行为显现。

例如：
- 不直接宣布人物震惊，而是写他没有完成原本熟悉的动作。
- 不直接宣布人物关心另一个人，而是写他记住了对方随口提及的需求。
- 不直接宣布人物不信任某份档案，而是写他反复核对某个细节，却始终没有把档案交出去。

但不要机械禁止情绪词。人物在适当场景中可以明确感到愤怒、恐惧、悲伤或喜悦。

判断标准不是“有没有写出情绪”，而是情绪是否可信、是否符合人物，以及是否被过度解释。

### 4.4 信息的间接呈现

在合适的场景中，可以通过以下形式揭示信息：

- 不完整的谈话；
- 不同人物对同一事件的矛盾叙述；
- 课本与亲历者记忆之间的差异；
- 被修改、缺页或无法核实的档案；
- 人物对某个词语、动作或物件的不同理解；
- 技术现象与历史证词之间逐步建立的联系。

间接呈现不是隐藏一切。

如果读者无法判断人物为什么行动、某项证据意味着什么，或场景冲突在哪里，就需要补足必要信息。

### 4.5 对话

每段对话至少应有一个明确作用：
- 推动行动；
- 暴露人物差异；
- 造成误解；
- 改变关系；
- 提供或扭曲信息；
- 迫使人物作出选择。

人物不必说出全部想法，但必须有自己的交流目的。

禁止让人物为了向读者讲解世界观，突然使用不符合其身份和情境的说明性长篇独白。

也不要为了追求含蓄，让所有人物都说半句话、频繁停顿或刻意回避问题。

直截了当、争吵、玩笑和明确拒绝同样可以成立，前提是符合人物性格和场景压力。

### 4.6 意象与重复

声音、物件、动作和地点可以反复出现，但每次重复应当经过判断。

例如，同一种机器声音在不同章节可以依次成为：
- 日常环境的一部分；
- 某种无法解释的异常；
- 与历史证词相互印证的线索；
- 人物对过去形成新理解的触发因素。

不要为了呼应而重复同一句比喻或相似描写。

每次重复至少应满足一项：
- 增加新的事实；
- 改变人物对它的理解；
- 改变它在读者心中的意义；
- 推动人物关系或情节发生变化。

若重复没有带来新的意义，优先删减。

## 5. 场景设计

每个场景开始前，明确以下内容：

1. **目标**：焦点人物当前想完成什么？
2. **阻力**：是什么阻止他直接达成目标？
3. **行动**：人物采取了什么具体行动？
4. **变化**：场景结束时，什么发生了改变？
5. **余波**：变化如何影响下一场景？

场景不必每次都包含重大事件。食堂、课堂、宿舍、实验室和矿井中的普通生活同样重要。

但生活场景不能仅仅展示世界观。它应当让人物的偏见、习惯、能力、关系或处境在具体互动中显现。

对于 AScombat，优先通过生活场景体现：
- 火烤与水煮之间的日常差异；
- 火盟和水盟学生的习惯及偏见；
- 塔连与玛伦在做事方式上的差异；
- 雷恩在两盟关系之外的处境；
- 学生之间从不信任到有限合作的过程。

避免把场景写成设定展示台。

## 6. 历史线索与证据控制

涉及矿难、档案、证词或汽相异常时，必须区分：

- **事实**：在作者掌握的故事真相中实际发生了什么。
- **证据**：人物能够获得的记录、痕迹、物件或证词。
- **解释**：人物根据证据形成的结论。
- **可信度**：该证据有多可靠，以及它能够支持什么结论。
- **认知状态**：人物目前相信什么，仍怀疑什么。

一份证据可以真实存在，但无法证明人物认为它证明的事情。

一份证词可以包含真实记忆，同时遗漏其他重要事实。

两份材料相互矛盾时，不要自动选择戏剧性更强的版本。应核查矛盾是否有既定解释，或者是否需要作者作出新的设定决定。

揭示历史真相时，按以下顺序检查：

1. 当前证据来自哪里？
2. 谁能够接触它？
3. 谁知道它的存在？
4. 人物如何解释它？
5. 读者此刻能够合理得出什么结论？
6. 该结论是否提前越过当前的信息层级？
7. 后续剧情是否能够回收这一线索？

不得只为制造悬念而故意让人物忽略明显且符合其能力的证据。

## 7. 汽相技术的叙事控制

汽相既是技术主线，也是人物合作与政治争夺的隐喻。

技术发展应遵守既定阶段：
1. 发现汽相；
2. 驯化汽相并推动活塞；
3. 建立稳定循环；
4. 理解这种力量来自不同属性的协作关系。

技术进步应当通过实验、失败、观察、修正和合作体现，不应由主角一次灵光一闪解决所有问题。

写技术场景时，检查：
- 当前阶段允许实现什么？
- 现有设备、材料和魔法能力是否足够？
- 实验失败的原因是否具体？
- 角色的专业能力是否互补？
- 技术成果是否改变人物关系或利益分配？
- 民用可靠性与军事化之间的冲突是否真实存在？

早期只呈现必要的异常和可观察现象，不要提前解释全部原理。

但不得为了保留谜团而违反已经确定的技术规则。

## 8. 人物连续性

创作前读取相关人物档案和最近章节，建立简短的人物状态表。

至少记录：
- 当前目标；
- 当前恐惧或顾虑；
- 已知事实；
- 错误判断或未证实的猜测；
- 对其他人物的信任与戒备；
- 已经作出的承诺；
- 当前不能公开的秘密；
- 本章可能发生的变化。

人物行动必须与其认知和动机一致。

若人物改变立场，应有足够的事件、证据、情感经历或利益变化作为支撑。

不得仅为了让剧情继续而让人物突然变得愚蠢、健忘、轻信或无故背叛。

人物可以犯错，但错误应源于其有限信息、性格缺陷、利益冲突或情绪压力。

塔连、玛伦和雷恩不能被简化为火、水、风光三种立场的代言人。他们必须拥有超出阵营标签的个人目标、习惯、缺点和矛盾。

## 9. 创作工作流

### 阶段 A：理解任务

先判断用户要求的是：
- 新写章节；
- 续写现有章节；
- 修改文风；
- 重构场景；
- 检查人物或历史连续性；
- 审查章节大纲；
- 更新项目设定。

不要将局部润色擅自扩大成整章重写，也不要在用户要求写正文时只给出创作建议。

### 阶段 B：建立创作上下文

读取相关的规范、章节大纲、前后文和人物档案。

整理以下信息：
- 当前时间、地点和视角人物；
- 当前场景的目标与冲突；
- 读者已知信息；
- 焦点人物已知信息；
- 当前允许揭示的信息层级；
- 必须保留的事实；
- 本章结束时必须发生的变化。

若关键事实缺失且会影响故事正确性，先向用户询问，或明确列出待确认事项。不要凭空补造重要设定。

### 阶段 C：先规划变化，再写正文

先写一份简短的场景计划。

每个场景说明：
- 场景目的；
- 人物行动；
- 核心阻力；
- 信息变化；
- 关系变化；
- 场景结尾。

若一个场景没有推动事件、人物关系、读者认知或主题中的任何一项，应考虑删除、合并或重新设计。

### 阶段 D：撰写正文

直接进入人物正在经历的场景。

优先通过动作、对话、物件和环境呈现信息，避免先写大段世界观说明。

保持句式和节奏变化。允许安静场景，也允许快速冲突。不要强迫每段文字都含蓄、每个细节都象征化。

写完一个场景后，检查人物的行动是否真实改变了局面。

### 阶段 E：修订正文

按顺序执行四轮检查：

**第一轮：剧情**
- 事件是否清晰？
- 人物为什么采取行动？
- 冲突是否真实？
- 场景结束时是否发生变化？

**第二轮：人物**
- 人物是否掌握了不该知道的信息？
- 行动是否符合其目标和缺点？
- 关系变化是否有充分依据？
- 对话是否具有个人差异？

**第三轮：叙事**
- 是否有过度解释？
- 是否有不必要的重复？
- 情绪是否被反复命名？
- 信息揭示是否符合当前阶段？
- 悬念是否建立在有效证据上？

**第四轮：语言**
- 删除空泛形容词和无意义修饰；
- 修正不自然的中文表达；
- 调整机械重复的句式；
- 保留真正有作用的感官细节；
- 朗读关键对话，检查人物声音是否自然。

### 阶段 F：一致性检查

完成正文后，检查它与既有设定的关系。

至少核对：
- 时间、地点与事件顺序；
- 人物身份和称谓；
- 人物知道与不知道的内容；
- 魔法和汽相技术的限制；
- 历史证据及其来源；
- 读者信息层级；
- 已经建立但尚未回收的线索；
- 与前文重复或矛盾的描述。

区分真正的错误与有意设置的叙事差异。不同人物可以对同一事实持有不同看法，但作者必须知道这种差异是否有依据。

## 10. 项目文件修改规则

默认先完成正文或提出修订方案，再决定是否更新规范。

- 仅润色正文时，不要无故修改 `docs/` 或 `data/`。
- 新增章节时，遵守 `drafts/chapterNN.md` 的命名约定，并同步更新 `drafts/manifest.json`。
- 新增正式设定时，先判断它是否与现有规范冲突，再更新对应的 `docs/` 文件。
- 修改结构化数据时，必须验证 JSON 合法性，并检查字段含义和相关 ID。
- 发现规范与正文冲突时，先报告冲突，不要自动把正文提升为规范。
- 不得将未确认的推测写成正式历史事实。
- 遵守 `AGENTS.md` 中的 Git 操作和提交要求；不得声称已提交或推送，除非实际操作成功。

每次变更应尽量局部、可追踪，避免一次修改多个不相关的设定领域。

## 11. 交付标准

用户要求正文时，优先交付可以直接阅读、编辑或保存的完整正文，而不是只交付分析。

若用户要求修订现有文本：
- 保留原文中有效的情节和人物特征；
- 不擅自改变关键事实和剧情结果；
- 对实质性改动给出简要说明；
- 必要时指出仍需作者决定的问题。

若用户要求一致性审查：
- 明确指出冲突位置；
- 说明冲突类型及其影响；
- 区分确定错误、潜在风险和主观建议；
- 提供可执行的修订方案。

不要在每次正文交付后附上冗长的文学理论说明。

## 12. 最终质量门槛

完成任务前，逐项确认：

- [ ] 正文遵守项目事实与世界规则。
- [ ] 人物只根据当时可获得的信息行动。
- [ ] 当前章节没有无意泄露更高层级的历史真相。
- [ ] 场景有明确目的、阻力和结果。
- [ ] 人物关系或读者认知至少有一项发生有效变化。
- [ ] 情感表达自然，不依赖反复命名。
- [ ] 对话符合人物身份、目标和情境。
- [ ] 意象与细节没有机械重复。
- [ ] 技术表现符合汽相发展阶段。
- [ ] 没有为了悬念而牺牲因果逻辑。
- [ ] 所有必要的文件变更均已说明和校核。

质量门槛不是要求每个场景都具备所有文学技巧，而是确保每个技巧都有明确的叙事理由。

最终目标是：**让读者通过人物的生活逐渐理解世界，通过人物的选择重新理解历史，并在故事结束后仍然能够思考那些没有被简单解决的问题。**
